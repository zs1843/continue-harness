# 通用 Harness 目标设计

## 目标

`continue-harness` 的核心不是创建某种前端项目，而是为任意软件项目提供一套可交接、可验证、可追溯的协作约束。

项目可以是前端、后端、客户端、数据、基础设施或混合系统；可以使用任意语言、框架和构建工具。技术栈只作为项目事实和可插拔适配器存在，不进入通用模板的默认内容。

最终目标是：任何人员或 Agent 在中途接手时，都能基于结构化上下文准确理解当前状态、约束、决策、证据、未完成项和验收标准，并继续实现而不依赖口头记忆。

## 核心边界

```text
通用 Harness Core
  ├─ 项目事实与约束
  ├─ 多轮 Intake 与输入确认
  ├─ 需求、任务、决策、变更的追溯关系
  ├─ 上下文快照与恢复
  ├─ 结构化日志与报告
  ├─ 自动化检查编排
  ├─ 验收标准与覆盖闭环
  └─ Adapter 扩展协议

项目适配层
  ├─ 语言与框架
  ├─ 构建、测试、Lint、部署命令
  ├─ 运行时检查
  ├─ 平台验收规则
  └─ 产品或领域特有输入
```

Core 不应导入 Vue、uni-app、React、Java、Go、Node、H5 或任何具体 UI 组件库。已有 `consumer-h5`、`web-mobile` 和 `uni-app` 应降级为可选 Adapter/Preset，而不是默认项目形态。

## 通用模板原则

默认 `create` 只创建约束容器，不创建业务页面、示例 API、示例组件或技术栈依赖。通用模板可以包含：

- `AGENTS.md`：唯一约束本体。
- `.continue-harness/project.yaml`：项目事实、输入策略、命令和验收配置。
- `.continue-harness/inputs/`：原始证据登记入口。
- `docs/PROJECT.md`：项目目标、范围和非目标。
- `docs/DECISIONS.md`：持续影响实现的架构决策。
- `.continue-harness/logs/commands.ndjson` 和任务历史：记录可追溯的命令、验证和交接事实；需要面向用户的变更日志时再按项目需求启用。
- `docs/ACCEPTANCE.md`：验收标准和覆盖状态。
- `docs/history/`：任务历史、快照和上下文交接记录。
- `.continue-harness/logs/`：命令与 Agent 运行日志目录。

以下内容只能由项目适配器或项目输入按需提供：

- `src/`、`app/`、`cmd/` 等代码目录。
- 语言、框架和构建工具配置。
- UI、视觉 Token、页面流和截图基线。
- API 描述、数据库迁移和部署配置。
- 具体业务状态、品牌值和领域规则。

## 多轮 Intake

创建新项目不应一次询问所有输入，也不应把某个产品形态当成默认答案。Intake 是一个有状态的事实收集流程。

### 第一轮：项目基本信息

只确认影响整体约束结构的事实：

- 项目名称和目标目录。
- 项目目标、范围、非目标和主要交付物。
- 项目类型：前端、后端、客户端、数据、基础设施或混合项目。
- 运行环境和部署目标。
- 语言、框架、构建工具、包管理器和测试工具；未知时记录为待确认。
- 参与角色、交接对象和协作方式。
- 现有仓库、文档、Issue、设计、API 或其他证据位置。

这一轮只形成项目事实，不创建业务任务，也不补写用户没有提供的结论。

### 第二轮：按项目类型确认输入

Harness 根据第一轮事实生成最小必要输入清单，而不是固定要求所有目录：

| 项目类型 | 默认询问 | 不默认询问 |
| --- | --- | --- |
| 前端 / 客户端 | 需求（必需）；按任务确认 RP/UI、视觉依据、API、资产 | 数据库迁移 |
| 后端 / 服务 | 需求、领域规则（必需）；按任务确认 API 合约、数据模型、部署环境、非功能指标 | UI、视觉 Token |
| 数据 / 算法 | 目标、数据来源、数据契约、评估指标、运行环境、资源约束 | UI、页面流 |
| 基础设施 | 目标架构、环境、资源、权限、变更窗口、回滚标准 | PRD、视觉稿 |
| 混合项目 | 按已确认的子系统拆分输入并标注归属 | 无条件复制全部输入类型 |

每一项输入都要记录 `required / optional / not_applicable / pending` 状态和理由。未适用不是缺失，待确认也不能伪装成已确认。

### 后续轮次：只追问阻塞事实

之后每轮只处理：

- 当前任务无法继续所缺少的事实。
- 多个输入之间的冲突。
- 会改变架构、验收或安全边界的决策。
- 用户必须确认的延期、外部阻塞或风险接受。

每轮结束时保存 Intake 状态、已确认事实、待确认问题、来源和下一步动作，允许新的 Agent 无损恢复。

## 统一追溯模型

所有项目使用同一条可追溯链，不依赖技术栈：

```text
原始输入
  → 已确认事实
  → 约束 / 决策
  → 需求节点
  → 任务
  → 变更
  → 测试证据
  → 验收标准
  → 报告 / 快照
```

每个节点至少包含：稳定 ID、来源、版本或哈希、当前状态、负责人或执行 Agent、时间、关联节点和未决风险。

Agent 不应只读取“最新对话”。接手时应从当前任务、最近快照、有效输入、持久决策、未决问题、最近日志和验收覆盖中恢复上下文。

## 日志与上下文管理

日志分为三层：

1. `command log`：命令、参数摘要、环境、开始/结束时间、退出码、标准输出摘要和产物路径。
2. `agent run log`：本轮目标、读取的事实、采取的动作、修改文件、验证结果、失败重试和下一步。
3. `decision log`：长期有效的选择、备选方案、依据、影响范围和复审条件。

日志不得默认写入凭据、Token、完整敏感请求体或用户隐私。日志应支持按任务、时间、命令和结果检索，并由快照记录关键日志的哈希或引用。

上下文分为：

- `canonical`：项目约束、已确认事实、有效输入和持久决策。
- `task`：当前任务目标、范围、验收标准、相关输入和变更。
- `ephemeral`：本轮对话、临时推断和工具输出。

只有经过确认或写入决策/任务记录的内容，才能从临时上下文升级为可供后续 Agent 依赖的事实。

## 通用验收闭环

验收不等同于“执行了某个框架的 build”。通用 Harness 至少提供：

- 需求节点是否都有验收标准。
- 每条验收标准是否绑定测试或其他可审计证据。
- 每个失败是否有日志、原因和重试记录。
- 未完成项是否明确标记为 `pending`、`deferred` 或 `blocked`。
- 延期和阻塞是否有确认人、理由和后续条件。
- 报告是否能从结果回链到输入、任务和决策。

适配器可以增加构建、运行时、视觉、接口或部署检查，但不能替代通用闭环。

## 目标 CLI 流程

```text
continue-harness create <name>
  → 第一轮项目基本信息
  → 生成最小通用约束容器
  → 第二轮按项目类型生成输入清单
  → 登记与确认原始证据
  → 创建任务和验收标准
  → 执行适配器命令与通用闭环检查
  → 生成日志、报告、快照
  → resume 恢复上下文
```

技术栈未知时允许先创建通用容器；技术栈确认后再安装或启用对应 Adapter。Harness 不应因为缺少 UI、API 或某种语言信息而错误阻塞创建，也不应在事实不足时生成技术栈模板。

## 迁移顺序

1. 新增通用约束模板和 Intake 状态模型，不改变现有 H5 preset。
2. 让 `create` 默认进入通用模式，`consumer-h5` 改为显式 preset。
3. 将 Doctor、Inputs、History、Resume、Verify 的通用部分从 `consumer_h5` 条件中抽出。
4. 增加结构化日志、上下文引用和通用验收闭环。
5. 将 H5/uni-app 检查移动到 Adapter，并补充非 H5 fixture。
6. 重新生成 `chs-demo` 作为通用项目，保留独立 H5 fixture 做适配器验证。

迁移期间不删除已有 `.continue-harness` 文件，不把现有项目强制转换为通用模式；先通过显式配置和报告标记兼容状态。
