# 通用 Harness 设计原则

## 目标

Continue Harness 面向不同类型的软件项目，解决需求到验收的闭环、协作记录可追溯，以及项目级上下文可恢复的问题。无论由谁接手，都应能从记录中确定当前事实、约束、决策、证据、风险和下一步。

## 统一闭环

```text
项目事实
  → 适用输入
  → 已确认需求
  → 实现项
  → 验收项
  → 验证证据
  → 报告、日志与交接状态
```

Core 维护稳定标识、关联关系、状态和证据引用。项目负责定义真实需求、权威来源、实现边界及检查方法。未提供或不适用的输入要如实记录，不得由 Harness 补造事实。

## 多轮 Intake

### 第一轮：项目基本信息

确认项目目标、范围、交付物、项目类型、运行与交付环境、已知实现约束、协作角色、现有资料位置。未知项标记为待确认，不据此生成假设性要求。

### 第二轮：按项目事实确定输入

根据第一轮结果和当前任务，提出可能相关的输入项，并逐项确认适用性。需求材料通常需要明确；其他输入类别仅在项目类型、任务范围或用户确认表明相关时纳入。每项记录来源、状态、理由、版本或指纹及关联任务。

### 后续轮次：处理阻塞事实

只追问会影响实现、验收、安全边界或交付判断的未知项和冲突。Intake 状态、已确认事实、待处理问题和下一步均应持久化，以供后续会话恢复。

## 记录与恢复

协作记录至少覆盖：

- 项目约束与已确认事实。
- 输入清单及适用性。
- 任务、实现项和验收项的关联。
- 命令与验证结果、报告和关键日志。
- 决策、未决风险、延期或外部阻塞。
- 可恢复快照及下一步动作。

日志不得默认保存凭据、访问令牌、完整敏感请求或个人隐私。临时推断不能自动升级为项目事实；需经确认并落入权威记录。

## 验收原则

验收不等同于某条检查命令成功。闭环至少要求需求有可判断的验收标准，适用输入与验收项可追溯，检查结果有可复核证据，失败、延期和阻塞状态明确，交接能恢复当前结论。

项目自行声明检查命令。Harness 执行已配置的命令并维护结果，不推断项目使用的语言、框架、工具或部署方式。未配置检查不能标记为通过。

## 默认创建边界

新建流程生成约束与协作记录容器，不生成业务功能、示例页面或实现结构。输入类别和检查配置通过 Intake 确认；现有项目接入时优先复用已有资料，不覆盖项目文件。

## 当前实现边界

当前版本提供 Intake、输入登记与分析、任务历史、上下文恢复、验收关联校验、配置命令执行、日志与报告等能力。专门化检查及生成能力仅在相应实现和项目证据存在时启用。真实 Pilot 的结果和未通过项以[复验记录](../site/continue-harness-docs/docs/showcase/real-project-pilot.md)为准。
