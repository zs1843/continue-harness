# 验证模式

本页说明常用验证模式及其结果语义。命令入口见[命令](./commands.md)。项目也可配置其他模式名；只有 feature 和 audit 应用验收闭环门禁。

## quick

快速反馈模式，按配置顺序执行检查。默认在首个非通过结果处停止；显式设置 `fail_fast: false` 可继续执行。

## feature

功能验收模式，执行已配置检查并应用需求到验收项的闭环门禁。已配置的 Intake 未确认、关联缺失或存在未收口验收项时，不能报告为通过。

## runtime

运行时检查模式，仅执行项目显式配置的命令，不推断项目运行方式。

## interaction

交互检查模式，仅执行项目显式配置的命令，不自动判断交互是否完整。

## visual

视觉检查模式，执行项目配置的命令。Harness 没有统一的基线前置检查；基线存在性及视觉结果由项目命令检查。当前实现按输出中的特定文本识别缺失基线并标记 `not_configured`，识别范围有限。命令成功不能单独证明已有有效基线或视觉验收通过。

## audit

审计模式，执行本模式配置的命令并应用验收闭环门禁；不会自动汇总其他模式。需要在失败后继续收集结果时，必须显式设置 `fail_fast: false`。未设置时仍默认遇到首个非通过结果停止。

## 配置与状态

模式在 `.continue-harness/project.yaml` 的 `verify` 中映射到项目命令。完全缺少模式定义时，命令报错、退出码为 1，不生成本次报告；显式设置 `status: not_configured` 时生成未配置报告。空命令列表不属于有效的可执行模式配置。

- `passed`：本次配置的命令均通过；feature、audit 还要求其验收门禁通过。
- `failed`：命令未全部通过，或适用的闭环门禁存在缺口。
- `blocked`：单项检查被识别为环境阻塞，或验收记录存在已确认的延期、阻塞；整体验证结果仍可能是 `failed`。
- `not_configured`：模式显式标为未配置，或 visual 输出命中缺失基线的识别规则；不能当作通过。

功能和审计模式检查当前任务及适用输入的验收关联。绑定任务但缺少验收记录、无效状态、缺少关联或未解决项会阻止通过。已确认延期或外部阻塞保留在报告中，不计为已验证。无 Intake 的旧项目保留兼容路径，不代表项目事实已经确认。

## 执行稳定性

执行前后会比较已绑定的配置、输入、实现、证据和验收记录指纹。前后状态不同会使本次验证失败。比较不是文件系统锁，也无法发现执行期间修改后又恢复原样的情况。

环境阻塞识别只覆盖部分进程启动错误和端口权限错误；其他外部条件可能仍显示为命令失败，需要结合原始日志审查。
