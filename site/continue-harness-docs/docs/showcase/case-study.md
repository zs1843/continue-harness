# 项目案例：从零构建前端工程 Harness

> 资料口径：基于仓库的 `0.1.0` 实现和 2026-09-21 的本地验证。已有项目跑通过这套流程（据项目讨论确认）；该项目的报告、截图和效果数据尚未收录到此仓库。

## 一句话介绍

`continue-harness` 是一套业务无关的项目协作与质量工具。它把项目输入、配置、Agent 工作流、任务历史、恢复状态和验证报告连接到同一个 CLI 协议，当前仓库已内置并验证的组合是 `consumer-h5 + web-mobile + uni-app`；这不是 Core 对技术栈的限制。

## 为什么做

前端项目在使用 AI 辅助开发时，常见问题不只是“代码能否生成”，还包括：需求和 UI 证据散落、不同 Agent 读取不同规则、只验证首屏而遗漏深层流程、生成代码覆盖手工修改，以及验收结论无法复现。这些是本项目希望解决的**问题假设**；已跑通项目的前后对照数据尚未整理进仓库。

目标是让开发者、CI 和 Agent 使用同一套项目事实与验证入口，同时由目标项目持有业务、接口和设计决定。Harness 负责约束和执行机制，不替项目作业务判断。

## 当前交付范围

| 能力 | 已实现的证据 | 边界 |
| --- | --- | --- |
| 创建与接入 | `create` 生成 Consumer H5 项目；`init` 先做完整 preflight，冲突时不写入 | 还没有 upgrade 和三方合并 |
| 项目诊断 | `inspect` 输出项目事实；`doctor` 只读检查环境、脚本、页面注册、输入和 Agent 工作流 | CI 入口及敏感内容检查仍不完整 |
| 验证与报告 | `quick`、`feature`、`visual`、`audit`；Markdown、JSON 和命令日志 | 视觉验收需要项目提供基线和真实流程 |
| 需求闭环 | 活跃 PRD 的页面、状态、动作与返回路径需要逐项记录验证、延期或外部阻塞 | 已跑通项目的覆盖记录尚未收录，无法据此评估深层流程效果 |
| 输入与 API | 登记 PRD/RP/UI/API/assets；从本地 OpenAPI JSON 按任务生成类型与请求封装，并保护手改文件 | 不支持在线 Apifox 同步和完整 OpenAPI 特性 |
| Agent 协作 | `AGENTS.md` 作为唯一约束本体；Skills 按任务加载 | 跨 Agent 的实际提效尚无量化数据 |

实现入口可从仓库的 `docs/PROJECT_MAP.md` 和 [Core 说明](../architecture/core.md) 开始看；当前状态以仓库的 `docs/CURRENT_STATUS.md` 为准。

## 架构判断

```text
开发者 / CI / Agent
        │
        ▼
      CLI ──────► Core：配置、诊断、执行、报告
                    │
                    ├─ 项目配置：选择能力、映射项目命令
                    ├─ Profile：产品形态检查
                    ├─ Platform：运行环境验收
                    ├─ Stack：框架工具链规则
                    └─ 可选 UI System：组件语义和 Token 映射
```

Core 只理解通用协议，不导入具体 Profile、Platform、Stack 或业务项目。这样，消费型 H5 的需求闭环、移动 Web 的运行环境、uni-app 的页面注册可以分别演进。代价是协议和配置层更多，早期项目需要维护清晰的边界和文档。[架构总览](../architecture/overview.md) 说明了依赖方向。

### 三个设计取舍

1. **项目事实留在项目内。** `.continue-harness/project.yaml` 选择验证命令和适配器；PRD、UI、API 与 Token 由目标项目保存。这样 Harness 可以复用，但必须处理输入缺失、冲突和版本追溯。
2. **写入前可预览。** `create/init` 提供 plan 或 dry-run；已有项目的初始化会先检查全部目标文件，发现冲突就停止写入。它保护已有项目，但目前不会自动生成合并补丁。
3. **让“完成”有可检查的定义。** `feature/audit` 不把构建成功等同于需求完成；活跃 PRD 的覆盖行必须有验证结果或明确原因。它能阻止明显遗漏，但覆盖质量仍取决于输入分析和人工确认。

## 一条完整工作流

```text
创建或接入项目
  → 登记 PRD / RP / UI / API / assets
  → 分析冲突并确认任务依据
  → 创建稳定任务 ID 和快照
  → 按任务实现，必要时生成 API 类型
  → 执行对应 verify mode
  → 保存报告、覆盖结论和任务历史
```

这条链路的价值是让“依据什么做、做了什么、如何证明完成”可以追溯。默认路径保持 `create/init → inputs → task → verify`；UI System、Design Token 和 OpenAPI 能力按任务启用，避免每个项目一开始就承担全部配置成本。

## 当前验证与实际成果

- 2026-09-21 在仓库根目录执行 `pnpm test`：**56/56 通过**；执行 `node packages/cli/bin/continue-harness.mjs version`：输出 `0.1.0`。
- 自动化测试覆盖配置、CLI、Doctor、初始化冲突保护、OpenAPI 生成保护、需求闭环，以及两种不同流程形态的 fixture。
- 仓库包含一个最小 uni-app H5 集成样例和 Playwright 运行检查；文档站可静态构建。

这些结果证明当前实现有自动化回归保护。已有项目跑通过工作流，但本仓库尚无对应的可核验数据，因此不能据此计算交付速度、视觉还原率或 Agent 成本的改善。两个流程 fixture 也不等同于两个无关的真实项目。

## 当前风险与下一步

| 风险或缺口 | 下一步验证方式 |
| --- | --- |
| 输入分析偏启发式，PDF、图片和复杂 RP 需额外解释 | 从已跑通项目整理误判与人工修正记录 |
| UI System 与视觉流程的实际效果尚未收录 | 补入首次与最终截图差异、迭代次数、人工调整数 |
| 本地 OpenAPI 导出尚未覆盖复杂规范 | 整理无法生成的 operation 和手工补充点 |
| 尚未发布，`@company` 仍是占位 scope | 确定 registry 后做 tarball 安装验证，再决定内部预发布 |

下一步是把已跑通项目的 PRD/UI 依据、运行与验证记录整理成可公开的实例，再根据过程中遇到的问题反推通用检查。后续是否扩展 Merchant H5、Admin Web 等 Profile，应由无关项目的需求和验证结果驱动。详情见仓库的 `docs/ROADMAP.md`。
